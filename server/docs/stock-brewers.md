# Connect a brewer running factory firmware

Use a Hub build that includes the stock Pico and Z connections described here. The published v1.0.0 Hub already includes stock Zymatic recipe sync and stock Z Program Maker file export. The Pico and Z adapters below run in the Hub and leave the brewer's firmware in place.

| Stock firmware | How it connects | What the owner can do |
| --- | --- | --- |
| Pico S, Pro and C, 0.1.34 protocol | The brewer requests recipes and reports sessions to the Hub over LAN HTTP. | Publish recipes by brewer, optionally associate a physical tag, and review the brew journal. |
| Z module with the 0.0.119 Program Maker | The Hub connects to the module's private IPv4 address on port 80. | Read the current state, stage one compatible working recipe and offer a saved recipe to a Hub group. |
| Zymatic 1.1.14 | The brewer fetches the owner's recipe menu over LAN HTTP. | Publish recipes and cleaning programs and follow reported temperatures, steps and errors. |

Keep these original HTTP services on the owner's LAN. The local protocols and journal paths have software tests. Confirmation of display behavior, installation-specific networking and brewing on physical machines requires an operating trial. [Stock Zymatic setup and hardware check](stock-zymatic.md) · [Standalone machine connections](device-connections.md)

## Pico S, Pro and C

1. Configure the DNS used by the brewer so `picobrew.com` resolves to the Hub computer or its LAN reverse proxy. Connect or restart the brewer with network access enabled. The brewer requests uppercase `/API/pico/` using plain HTTP on port 80. If the Hub runs on port 8080, have the LAN proxy forward `/API/` to it, preserving the path, query string and case. A browser reaching the Hub on port 8080 checks only the owner's route.
2. In **Brewery → Add machine → Add a stock brewer**, register the stock brewer using its 32-character hexadecimal UID. A recent registration request can supply the UID. Give it a name and select the model from the physical brewer, since the UID is shared protocol information across S, Pro and C. An unclaimed brewer can display a registration code. After enrollment, retry the connection on the brewer.
3. Open a saved recipe in the library, choose **Send**, select that named stock Pico and preview the recipe. For a surviving tag, use **RFID tag (optional)** to enter its 8, 14 or 20 hexadecimal characters. The mapping applies to this brewer. Use one tag per recipe on that brewer. Review the steps before selecting **Publish to brewer menu**. Republish after changing the library recipe.
4. Insert the step filter. If you have no PicoPak tag, cancel the tag search or let it time out to reach the recipe list. If you assigned a physical tag, scan it to fetch its recipe. Review the recipe and start at the dial. For compatible original kit programs, the adapter honors the recipe author's supported strength and bitterness adjustments. The Hub checks that the stock recipe format can represent the steps before publishing.

Under **Brewery → Stock brewers**, the Pico card shows its latest reported state and error with receipt times. Open **Brew journal** to see sessions reported by the named machine. The journal includes step and event text, wort and thermoblock readings in Fahrenheit, remaining step time, device state and reported errors. State and error messages identify the brewer, so the Hub associates them with its session active at receipt. A report of brew completion or cancellation records that outcome. An idle report alone records an end with unspecified outcome. The Hub uses its receipt time. Menu lookup and tag reads can happen before brewing, so a session alone does not establish which library recipe ran. JSON and CSV exports preserve the reported fields. [OEM Pico wire format](../../firmware/pico-s-pro/reverse-engineered/docs/network-recovery.md#http-and-application-payloads)

## Z Program Maker

1. On the intended Z, confirm the IP address and that the stock Program Maker website is available. In **Brewery → Add machine → Add a stock brewer**, register that module's private IPv4 HTTP address and a name. The Hub must have a network interface directly attached to that private network. Register each module of a stack separately. A DHCP reservation helps keep the address associated with the correct module. The website identifies the service and exposes readings, but does not report a unique module identity.
2. Open the registered module's live readings for temperatures, valve position, pump activity, current step, pause and timing when available. These readings come from the stock `/state` page and do not establish which recipe is loaded or that the brewer is idle.
3. In the library choose **Send**, select the named stock Z and preview the saved recipe. At the physical dial, verify that the intended module is idle. Confirm its address and choose **Replace working recipe** when you are ready to replace the single Program Maker working program. Check the recipe name on the receiving brewer and start it at the dial. If delivery is unconfirmed, check the dial before requesting another transfer. An acknowledgment means the stock endpoint accepted the upload. Original Z cloud and PicoPak adapter programs need compatible standalone Z firmware. You can also export compatible Program Maker JSON for manual import through the module's website. [Stock Z recipe formats](family-devices.md#z-recipes-and-front-panel)

A stock Z limits each kettle heating step to about 202 °F (94.45 °C). The Hub identifies those steps in the direct transfer and group invitation previews. The brewer can lower a target further to 2 °C below its estimated local boiling point. When it lowers a target for that reason, it extends holds longer than 10 minutes by 162 seconds per degree Celsius of reduction. This happens on the receiving module, so two modules can produce different hold times from the same program. [Original Z compiler behavior](../../firmware/z-series/reverse-engineered/analysis/program-recipes.md)

### Brewing with a group

In **Brewery → Group machines**, add each registered stock Z separately. After staging a compatible library recipe on a source Z, use **Offer recipe to [group]** to invite the other selected machines. Starting at the stock Z dial provides no recipe-start event to the Hub, so issue the offer yourself.

For a receiving stock Z, open the pending invitation in the Hub and choose **Review replacement**. Verify the recipient address, check that the brewer is idle, approve **Replace working recipe**, then review and start on that recipient's dial. Each module has a single working program. Stock recipients use the Hub invitation and ordinary Program Maker screen. The original Azure Group Session service is outside this integration. Standalone Z firmware supports native invitations for additional routines. [Group brewing by model](../../docs/firmware-parity.md#group-brewing)
